Modes模式

Seven modes, each answering a different question. Every example below is runnable as-is against a local vLLM/SGLang endpoint.七种模式，各自回答不同的问题。下面每个示例都可以直接对着本地 vLLM/SGLang 端点运行。

scenario default

Multi-turn long-context workload: N users, each growing its own conversation until compaction kicks in.

多轮长上下文负载：N 个用户各自维护不断增长的会话，直到触发压缩。

Answers: how does TTFT / TPOT degrade as a real conversation grows and several users share the server? Every turn appends to history, so the prefill grows turn by turn — the effect a single-shot benchmark misses.

回答的问题：当真实会话不断增长、多个用户共享服务时，TTFT / TPOT 如何劣化？ 每轮都会把新内容追加到历史，预填充量逐轮增长 —— 这正是单次请求压测看不到的效果。

Use it when you are validating a serving configuration for agent traffic, sizing concurrency, or checking that long-context decode stays within budget.

适用场景：为 Agent 流量验证服务配置、评估可支撑并发，或检查长上下文解码是否在预算内。

clawperf --mode scenario \
  --endpoint http://localhost:8000/v1 --model qwen3-32b \
  --tokenizer /mnt/model/Qwen3-32B \
  --context-profile medium \
  --num-users 8 --max-turns 20 --user-arrival poisson:2 \
  --metrics-endpoint http://localhost:8000/metrics --reset-cache \
  --output results_scenario.json

Context comes from --context-profile (or raw --system-prefix-tokens / --user-prefix-tokens / --input-tokens-per-turn). --max-context-tokens must match the model's real window, otherwise compaction triggers at the wrong time. 上下文由 --context-profile（或原始 --system-prefix-tokens / --user-prefix-tokens / --input-tokens-per-turn） 决定。--max-context-tokens 必须与模型真实窗口一致，否则压缩触发时机不对。

hitrate

Controlled prefix-cache experiment: prefill known prefixes, then measure the real cache hit rate and the speedup it buys.

受控前缀缓存实验：先注入已知前缀，再测量真实缓存命中率及其带来的加速比。

Answers: is prefix caching actually working, and how much does it help? The measured hit rate is read from the server's own Prometheus counters (prefix_cache_hits_total / queries_total), not inferred from prompt construction.

回答的问题：前缀缓存真的生效了吗？收益多大？命中率直接读服务端 Prometheus 计数器（prefix_cache_hits_total / queries_total）， 不是从提示词构造推断出来的。

Output: TARGET vs MEASURED hit rate, theoretical ceiling 1/(1-hit_rate) vs actual speedup, plus a per-engine breakdown.

输出：目标 vs 实测命中率、理论上限 1/(1-hit_rate) 与实测加速比，以及逐引擎明细。

clawperf --mode hitrate \
  --endpoint http://localhost:8000/v1 --model qwen3 \
  --num-requests 200 --input-len 8192 --hit-rate 0.7 --prefix-num 4 \
  --output-len 128 --concurrency 8 \
  --metrics-endpoint http://localhost:8000/metrics --reset-cache \
  --output results_hitrate.json

--hit-rate 0.7 and --prefix-len 5734 are two ways to say the same thing (they are mutually exclusive); --prefix-num controls how many distinct prefixes are in play, which is what makes a multi-tenant workload realistic. --hit-rate 0.7 与 --prefix-len 5734 是同一件事的两种写法（二者互斥）；--prefix-num 控制有多少个不同前缀， 这正是多租户场景真实感的来源。

slo

Concurrency sweep: raise the load step by step and report the largest number of users that still meets every latency constraint.

并发扫描：逐步加压，报告仍能满足全部时延约束的最大用户数。

Answers: "how many concurrent users can this deployment serve at ttft.p99 ≤ 1.5s?" — the capacity number you put in a plan, with the binding constraint named.

回答的问题：「在 ttft.p99 ≤ 1.5s 下这套部署能支撑多少并发？」 —— 可以直接写进方案的容量数字，并指出是哪条约束先被打破。

Output: a capacity curve (one column per constraint) plus Max sustained users. Steps that overrun --slo-step-timeout-s are reported as TIMEOUT and fail.

输出：容量曲线（每条约束一列）与「最大可支撑用户数」。超时（ --slo-step-timeout-s）的步会标记为 TIMEOUT 并判定不达标。

# shell-safe: ':' means '<='
clawperf --mode slo \
  --endpoint http://localhost:8000/v1 --model qwen3-32b \
  --slo ttft.p99:1500 --slo tpot.avg:30 --slo e2e.max:30000 \
  --slo-min-users 1 --slo-max-users 200 --slo-step-strategy geometric \
  --slo-step-turns 5 --slo-error-rate 0.01 \
  --output results_slo.json
| Users | ttft.p99 | tpot.avg |   e2e.max | Error | SLO |
|     1 |  228.2ms |    8.6ms |  8887.7ms |  0.0% |  ✓  |
|     4 |  624.2ms |   14.7ms | 15471.1ms |  0.0% |  ✓  |
|     6 |  945.1ms |   20.9ms | 22360.6ms |  0.0% |  ✗  |
SLO: ttft.p99<=1500ms, tpot.avg<=30ms, e2e.max<=30000ms
Max sustained users: 5

agent

Real agent-at-work performance: the model under test actually runs coding tasks — reading files, editing, running shell commands — through tool calls.

真实 Agent 工作负载：被测模型通过工具调用真正执行编码任务 —— 读文件、改代码、跑命令。

Answers: how does the server behave under the *shape* of agent traffic (bursty tool loops, long growing histories) rather than a synthetic prompt pattern?

回答的问题：在 Agent 流量的形态下（突发的工具循环、不断增长的长历史）， 服务端表现如何？而不是合成提示词模式。

Needs an OpenAI-compatible endpoint with tool calling enabled (vLLM: --enable-auto-tool-choice --tool-call-parser qwen3_xml).

依赖开启工具调用的 OpenAI 兼容端点（vLLM： --enable-auto-tool-choice --tool-call-parser qwen3_xml）。

clawperf --mode agent \
  --endpoint http://localhost:8000/v1 --model qwen3-32b \
  --agent-tasks 8 --agent-max-steps 12 --agent-max-tokens 512 \
  --agent-shell-timeout 30 \
  --output results_agent.json

trace

KV-cache analysis from a production trace, plus optional real replay of the trace's requests against your endpoint.

基于生产 trace 的 KV 缓存分析，并可选择把 trace 中的请求真实回放到你的端点。

Two halves. (1) Simulation: replay the trace's block hashes through a simulated LRU/FIFO cache to get hit rate, evictions and the hit-rate-vs-budget curve — no endpoint needed. (2) Real replay: if the trace carries messages, send them to --endpoint to measure TTFT/TPOT for that exact workload.

两半功能。（1）模拟：把 trace 的 block hash 送进模拟的 LRU/FIFO 缓存， 得到命中率、驱逐次数与「命中率-预算」曲线 —— 不需要端点。（2）真实回放：若 trace 带 messages， 则把它们发到 --endpoint，测出该真实负载下的 TTFT/TPOT。

Budget. --cache-budget-tokens or --cache-budget-gb (+--kv-bytes-per-token); --budget-sweep scans levels to find where returns flatten.

预算。--cache-budget-tokens 或 --cache-budget-gb（配合 --kv-bytes-per-token）； --budget-sweep 扫描多个预算档位，找出收益拐点。

# simulation only
clawperf --mode trace --trace-file trace.jsonl.gz --budget-sweep --eviction-policy lru

# simulation + real replay (clamped to the model window)
clawperf --mode trace --trace-file trace.jsonl.gz \
  --endpoint http://localhost:8000/v1 --model qwen3 --tokenizer /mnt/model/Qwen3-32B \
  --cache-budget-gb 40 --kv-bytes-per-token 2.0 --model-context-length 32768 \
  --trace-users 4 --output results_trace.json

record

A recording proxy: point a real agent (Claude Code, any OpenAI/Anthropic client) at it, work normally, and every request/response is written to JSONL.

录制代理：把真实 Agent（Claude Code 或任意 OpenAI/Anthropic 客户端）指向它，正常工作， 所有请求/响应写入 JSONL。

clawperf --mode record --proxy-port 9090 \
  --upstream-endpoint https://api.deepseek.com/v1 --upstream-api openai \
  --recording session.jsonl
# then point your agent at http://localhost:9090/v1

Anthropic clients are accepted too (/v1/messages) and translated to OpenAI on the fly. The file is appended across restarts, and you are told how many prior entries were kept. 也接受 Anthropic 客户端（/v1/messages），并实时翻译为 OpenAI 协议。 文件跨重启追加，并会提示保留了多少条历史记录。

replay

Replay a recording against any endpoint, preserving multi-turn history.

把录制内容回放到任意端点，并保持多轮历史。

--history-mode live (default, recommended): the server's actual response becomes the next turn's history, so the KV-cache prefix lines up with what really happened.

--history-mode live（默认，推荐）：把服务端真实返回 作为下一轮历史，使 KV 缓存前缀与真实情况对齐。

verbatim: send each recorded entry's messages exactly as recorded — useful for A/B comparing two servers on identical input.

verbatim：原样发送每条录制记录的 messages —— 适合在两个服务端之间做同输入的 A/B 对比。

clawperf --mode replay --recording session.jsonl \
  --endpoint http://localhost:8000/v1 --model qwen3-32b \
  --history-mode live --concurrency 4 --output results_replay.json

Context profiles上下文档位

A profile is a named context size — the human-friendly way to say "a typical coding session" instead of typing token counts. It sets three numbers:档位就是「命名的上下文大小」—— 用「典型编码会话」这样的说法代替手写 token 数。它一次性设定三个数字：

Which one should I use?该用哪个？

Start here. fresh for a smoke test, medium for a typical coding session, long / full for the tail of real sessions. xl and xxl are prefill stress tests — a single request can dominate the step, so use them on purpose.

怎么选。冒烟测试用 fresh；典型编码会话用 medium；真实会话尾部用 long / full。xl 与 xxl 属于预填充压力测试 —— 单个请求就可能主导整个步，请按需使用。

One profile per run. --context-profile sets a single size; to sweep sizes use --suite, which runs the (users × profiles) cross-product in sequence. --model-context-length skips any profile that cannot fit the model's window.

一次一个档位。--context-profile 只设一个档位； 想扫描多个档位请用 --suite，它会按序跑完（用户 × 档位）的笛卡尔积。 --model-context-length 会跳过放不进模型窗口的档位。

# one profile
clawperf --mode scenario --context-profile medium --num-users 8 ...

# sweep profiles × users
clawperf --mode scenario --suite full --model-context-length 32768 ...

# raw token counts instead of a named profile
clawperf --mode scenario --system-prefix-tokens 28000 \
  --user-prefix-tokens 10000 --input-tokens-per-turn 5000 --output-tokens-per-turn 1000 ...

Pacing & concurrency节奏与并发

Four knobs that are easy to confuse. The important distinction: a closed loop can never overload a server (the server throttles the load), an open loop can.四个容易混淆的旋钮。关键区别：闭环永远压不垮服务端（节奏由服务端决定），开环可以。

Knob参数Controls控制对象Semantics语义
--user-arrival burst|steady:<s>|poisson:<λ> when each session joins每个会话何时加入users then run their turns back-to-back加入后各自连续跑自己的轮次
--concurrency N closed-loop in-flight request cap (hitrate / replay / trace)闭环在途请求上限（hitrate / replay / trace）the next request starts as soon as one finishes上一个请求返回后立即发下一个
--request-rate R open-loop issue rate in req/s (Poisson)开环发送速率（req/s，泊松到达）requests are released on schedule regardless of completions按计划发送，与是否完成无关
--trace-users N session-level concurrency for trace replaytrace 回放的会话级并发turns inside one session stay ordered同一会话内的轮次保持有序
 
# open loop: 40 requests arriving at 2 req/s, no in-flight cap
clawperf --mode hitrate --endpoint http://localhost:8000/v1 --model qwen3 \
  --num-requests 40 --input-len 4096 --hit-rate 0.5 --request-rate 2

Metrics & PD disaggregation指标采集与 PD 分离

Pass one /metrics per instance. Counters are summed into a fleet-wide view, ratio gauges are averaged, and the per-engine table gains one row per instance (engine ids are namespaced by endpoint).每个实例各传一个 /metrics。计数器求和成全局视图，比率类指标取均值，逐引擎表按实例分行（引擎 id 以端点做命名空间）。

clawperf --mode scenario --endpoint http://lb:9000/v1 --model qwen3 \
  --metrics-endpoint prefill=http://10.0.0.1:9101/metrics \
  --metrics-endpoint decode=http://10.0.0.2:9102/metrics \
  --reset-cache

Labels are optional (name=url; default is host:port) and --metrics-endpoint is repeatable or comma-separated. --reset-cache resets every instance.标签可选（名称=url，默认 host:port）；--metrics-endpoint 可重复或用逗号分隔。--reset-cache 会逐个重置所有实例。

SLO constraint syntaxSLO 约束语法

<metric>.<agg><sep><ms> — repeat --slo to AND several constraints together. In a shell, quote <= or use a separator without </>, because those characters are redirections.<指标>.<统计量><分隔符><毫秒> —— 重复 --slo 可「与」多个约束。在 shell 中要么给 <= 加引号，要么改用不含 </> 的分隔符，因为这两个字符是重定向符号。

Write写法Means含义Notes说明
ttft.p99:1500ttft.p99 <= 1500msshell-safe (no quoting)免引号
tpot.avg=30tpot.avg <= 30msshell-safe (no quoting)免引号
'ttft.p99<=1500'ttft.p99 <= 1500msmust be quoted in bash/zsh在 bash/zsh 中必须加引号
ttft.p99:ge:1500ttft.p99 >= 1500msthe only shell-safe way to write >=唯一免引号的 >= 写法
'a<=1,b<=2'ttft.p99 <= 1ms AND tpot.avg <= 2msttft.p99 <= 1ms 且 tpot.avg <= 2msone quoted argument, several constraints一个引号参数写多条约束

Metrics: ttft (time to first token), tpot (time per output token), e2e (end-to-end latency).

指标：ttft（首 token 时延）、 tpot（每输出 token 时延）、e2e（端到端时延）。

Aggregates: avg, min, max, and any percentile p25 p50 p75 p90 p95 p99 p99.9. Several constraints AND together; the run stops the sweep at the first level that breaks any of them.

统计量：avg、min、 max，以及任意分位 p25 p50 p75 p90 p95 p99 p99.9。多条约束为「与」关系；一旦某一级打破了任意一条，扫描即在此停止。
